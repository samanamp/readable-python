Errors

Fail loudly at boundaries; decide recovery in one place.

RP10

Fail loudly at boundaries. Decide what's recoverable in one place.

Errors hidden deep in the code turn into wrong results far away from their cause. Recovery logic scattered everywhere means nobody knows what the system does when something breaks.

The blanket catch

The "before" loop survives everything, including a CUDA out-of-memory error, a corrupted model or a bug in outbox.put. It logs and carries on producing nothing, forever. The "after" loop handles the one failure it understands, a single session going bad, and lets everything else crash the process. Your process manager (Kubernetes, systemd) restarts it in a known-good state, and the crash shows up in monitoring.

Guidelines

Catch what you can handle, where you can handle it

Catch a specific exception type at the level that knows what to do about it. If the only thing you can do is log and re-raise, don't catch at all; the top level will log it.

One place decides recovery

Pick one layer (usually the main loop) that owns the policy: which errors end a session, which restart a worker, which crash the process. Lower layers raise; they don't decide.

Validate at boundaries, trust inside

Check input once, where it enters: the HTTP handler, the queue consumer, the config loader. Turn it into a typed object there. Code inside the boundary can then assume it's valid instead of re-checking defensively on every call.

@dataclass(frozen=True)
class Input:
    session_id: str
    keys: frozenset[str]

    @classmethod
    def parse(cls, raw: dict) -> "Input":
        keys = raw.get("keys", [])
        if not isinstance(keys, list) or not all(k in VALID_KEYS for k in keys):
            raise InvalidInput(f"bad keys: {keys!r}")
        return cls(session_id=str(raw["session_id"]), keys=frozenset(keys))

Define a few domain exceptions

A small hierarchy (CapacityError, SessionError, InvalidInput) makes "what can go wrong here" explicit and lets callers catch precisely. Don't create one class per call site.

Error messages name the thing and the value

raise ValueError(f"fps must be positive, got {fps}"), not raise ValueError("invalid config").

Never silence with pass

except SomeError: pass needs a comment saying why ignoring it is correct. If you can't write that sentence, don't ignore it.
