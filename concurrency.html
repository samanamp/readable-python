Concurrency and the GPU

Few threads, one owner per thread, overlap only what overlaps.

Concurrency is where readable code goes to die. Every extra thread, task or stream multiplies the orders in which things can happen. Use as little as the problem allows, and give each concurrent actor one clear job.

RP11

Each piece of mutable state belongs to one thread. Hand off with queues.

If only one thread ever touches the scheduler's state, it needs no locks and can be read like sequential code. Threads talk by passing immutable messages.

RP12

Only overlap work that uses different hardware, and prove it with a profile.

Concurrency helps when two things can really run at once: CPU next to GPU, a copy engine next to the SMs, a hardware encoder next to compute. Two compute kernels fighting over the same saturated SMs gain nothing and add jitter.

The basic shape for a serving process

Two actors, one queue in each direction:

  • The I/O side (an asyncio event loop) handles the network: HTTP, WebRTC, sockets. It never blocks and never touches model state. It puts typed messages on the inbox and takes results off the outbox.
  • The model side (one dedicated thread) owns the scheduler and the GPU. It runs a plain synchronous loop: drain the inbox, step, put results, wait for the next tick.
def start(model: Model, fps: float) -> tuple[Inbox, Outbox, Event]:
    inbox, outbox, stop = Inbox(), Outbox(), Event()
    scheduler = Scheduler(model, fps)
    threading.Thread(
        target=scheduler.run, args=(inbox, outbox, stop), name="model", daemon=True
    ).start()
    return inbox, outbox, stop

The scheduler's code contains no async, no locks and no executor plumbing. The only thread-safety lives in two queue classes, which are easy to test on their own.

Avoid: wrapping each call in async plumbing

The "before" loop lives on the event loop and hops every single call over to a worker thread. It works, but each line now carries scheduling noise, and the reader has to reason about two threads at every step. Move the whole loop to the thread instead.

GPU streams

A CUDA stream is an ordering queue, not extra compute. Work on a second stream runs concurrently only when the first leaves SMs idle. A well-written denoising or prefill step (large fused kernels, ideally captured in a CUDA graph) keeps every SM busy, so:

  • Don't put compute stages (decode, a second model, an encoder) on side streams expecting overlap. They only fill gaps, and they can delay the critical path and compete for cache and memory bandwidth.
  • Don't pipeline compute stages (decode step N−1 while denoising step N) unless a timeline shows idle SMs. If the GPU is saturated, pipelining adds a step of latency and saves nothing.
  • Do overlap work that uses other hardware: host↔device copies (copy engines), hardware video encode (NVENC), and CPU-side scheduling of the next step while the GPU runs this one. That last one is what SGLang's "overlap scheduler" does.
  • Do use CUDA graphs and fused kernels to remove launch gaps. That's usually worth more than any amount of stream juggling.

Guidelines

Never block the event loop

Anything that takes more than about a millisecond (model calls, file I/O, big serialization) doesn't run on the event loop. Send it to the model thread, or to a dedicated thread for that kind of work.

Threads have names and owners

Every thread you start is named (name="model"), and it's obvious from the code which object it runs and what state it owns. No anonymous pools for long-lived work.

Stop with an event, not cancellation

A blocking GPU call can't be interrupted. Pass a threading.Event and check it at the top of the loop, so shutdown finishes the current step and exits cleanly.

Keep the profile in the PR

Any change that adds a thread, stream, pipeline stage or cache includes before/after numbers: a timeline screenshot (Nsight Systems, torch.profiler) and the step time. No numbers, no concurrency.
