Good serving code has a recognizable shape. Open the scheduler in SGLang and the core loop is roughly: receive requests, process them, pick the next batch, run it, process the results. vLLM's engine step is similar: schedule, execute the model, update from the output. Each step is a method with a name that tells you what it does. Read the loop and you know the system; open a method only when you care about its details.

Rule 2. The top-level loop is a list of named steps. A reader should understand the whole system from one screen, then drill down only where they need to.
Rule 3. One class, one job. Data crosses boundaries as dataclasses. "Scheduler", "Executor", "Session" each answer one question. Typed data at the seams tells a reader exactly what one part hands to the next.

Before

A serving loop written as one long function. Everything works, and it's hard to read: dispatch, bookkeeping, error handling and pacing are interleaved, and the steps of the loop only exist as comments.

What makes it hard:

  • The shape of the loop exists only in the numbered comments.
  • Session state is spread across three containers that every branch must update together.
  • Messages are untyped dicts, so you learn their fields by reading every branch.
  • The helper _try_join takes the caller's dicts and changes them (see chapter 4).

After

The loop in run now reads as its own description: handle messages, build the batch, step, wait. Session state has one home. Messages are dataclasses (Join, Leave, Input), so match both dispatches and unpacks them. The pacing also became correct in passing: a running deadline doesn't drift the way sleep(interval - elapsed) does.

Guidelines

Name the steps after what they mean, not how they work

next_batch(), not filter_running_inputs(). A reader of the loop cares about the role of the step; the method body shows the mechanics.

Keep orchestration and work apart

The loop decides what happens and in which order. It shouldn't also contain the details of how. If a step needs more than a couple of lines inline, it's a method.

Typed data at every seam

Between the scheduler and the model, between the transport and the scheduler, between processes: use a @dataclass (or a protobuf/pydantic model at process boundaries). Avoid passing bare dicts with conventional keys. A dataclass is documentation the type checker enforces.

One file per concept, not per layer

A file called scheduler.py holding the scheduler is easy to find. A file called utils.py holding half of it isn't. Avoid utils, helpers, common and misc as homes for logic.
