Rule 14. Tests describe behaviour, one idea per test. The test suite is the specification people actually read. A test named after a behaviour, checking one thing, tells a newcomer what the system promises, and tells them exactly what broke when it fails.

Name the behaviour, not the function

Read only the names on the right and you know three promises the scheduler makes. When one fails, the name says which promise broke.

Guidelines

Arrange, act, assert

Each test sets up, does one thing and checks the result, in that order, with a blank line between the parts if it helps. No logic (loops, conditionals) in the test body. If you need a loop, use pytest.mark.parametrize.

Fakes over mocks

A small hand-written FakeModel with real behaviour (it returns a fixed token, or echoes the prompt) gives readable tests that survive refactors. Heavy mock.patch setups test the implementation's call sequence, and break whenever it changes.

Test the promises that matter most

For a batching generation server those are usually:

  • Progress: every running sequence gains exactly one token per step.
  • Order: waiting requests are admitted in arrival order.
  • Limits: a sequence stops at end-of-sequence or at max_new_tokens, whichever comes first.
  • Backpressure: a full queue rejects new requests cleanly instead of growing without bound.
  • Batch invariance: a request's output doesn't depend on which other requests shared its batch (with a deterministic fake model).

Fast by default

The core logic should be testable on a laptop CPU in seconds, with no GPU, network or model weights. Mark the slow, GPU-only tests (@pytest.mark.gpu) and run them separately.

Helpers that build, not helpers that assert

A make_scheduler(max_batch=2) factory keeps tests short. A custom assert_scheduler_ok(s) hides what's being checked; inline the assertions.
