Rule 14. Tests describe behaviour, one idea per test. The test suite is the specification people actually read. A test named after a behaviour, checking one thing, tells a newcomer what the system promises, and tells them exactly what broke when it fails.

Name the behaviour, not the function

Read only the names on the right and you know three promises the scheduler makes. When one fails, the name says which promise broke.

Guidelines

Arrange, act, assert

Each test sets up, does one thing and checks the result, in that order, with a blank line between the parts if it helps. No logic (loops, conditionals) in the test body. If you need a loop, use pytest.mark.parametrize.

Fakes over mocks

A small hand-written FakeModel with real behaviour (capacity, a deterministic output) gives readable tests that survive refactors. Heavy mock.patch setups test the implementation's call sequence, and break whenever it changes.

Test the promises that matter most

For a realtime serving loop those are usually:

  • Continuity: a session with no new input still gets output every tick.
  • Isolation: one session failing or leaving doesn't change another's output.
  • Boundaries: input arriving mid-step applies at the next step, never halfway through one.
  • Backpressure: a full model rejects new sessions cleanly instead of crashing.
  • Parity: a batched step gives the same output as stepping each session alone.

Fast by default

The core logic should be testable on a laptop CPU in seconds, with no GPU, network or model weights. Mark the slow, GPU-only tests (@pytest.mark.gpu) and run them separately.

Helpers that build, not helpers that assert

A make_scheduler(capacity=2) factory keeps tests short. A custom assert_scheduler_ok(s) hides what's being checked; inline the assertions.
