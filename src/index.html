Readable Python

A short style booklet for ML systems code: schedulers, engines, serving loops. It aims for the readability of codebases like vLLM and SGLang, where you can open the main loop and understand the system from one screen.

This is not a formatting guide. Let ruff format and a lint config settle spacing, quotes and import order, and never discuss them in review. Everything here is about structure: where state lives, how a loop is shaped, what a comment is for. Those are the things that make code easy or hard to follow, and tools can't fix them.

Each chapter gives a few rules and then a before/after example. The examples are small on purpose; the patterns scale.

The cheat sheet

  1. Optimize for the reader. Code is read far more often than it is written. When writing it is easy and reading it is hard, rewrite. → 1
  2. The top-level loop is a list of named steps. A reader should see the whole system in one screen. → 2
  3. One class, one job. Data crosses boundaries as dataclasses. → 2
  4. Every piece of state has exactly one owner. No parallel dicts kept in sync by hand. → 3
  5. Use an enum for status, not a pile of booleans. → 3
  6. Functions return results. They don't mutate their arguments. → 4
  7. One level of abstraction per function, and at most four parameters. → 4
  8. Name things with domain words, and use the same word for the same thing everywhere. → 5
  9. Comments say why. The code says what. Git says when. → 6
  10. Fail loudly at boundaries. Decide what's recoverable in one place. No blanket except Exception. → 7
  11. Each piece of mutable state belongs to one thread. Hand off with queues. → 8
  12. Only overlap work that uses different hardware, and prove it with a profile. → 8
  13. Add an abstraction at the second implementation, not the first. → 9
  14. Tests describe behaviour, one idea per test. → 10
  15. Review AI-written code for what to delete. → 11

How to use it

  • Reviewing: quote rules by number, e.g. "rule 4: who owns this dict?". It keeps reviews short and impersonal.
  • With coding agents: link the cheat sheet from AGENTS.md or CLAUDE.md. Agents follow concrete rules well, and chapter 11 lists what they tend to get wrong.
  • Breaking a rule: fine, when you can say why in one sentence. Put that sentence in a comment (rule 9).
