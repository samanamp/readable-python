The shape of a system

One loop you can read in one screen, built from named steps.

Good serving code has a recognizable shape. Open the scheduler in SGLang and the core loop is roughly: receive requests, process them, pick the next batch, run it, process the results. vLLM's engine step is similar: schedule, execute the model, update from the output. Each step is a method with a name that tells you what it does. Read the loop and you know the system; open a method only when you care about its details.

The examples in this booklet use one small system throughout: a text-generation server with continuous batching. Requests wait in a queue, get admitted into a fixed number of batch slots, gain one token per step, and free their slot when they finish.

"Scheduler", "Sequence", "SamplingParams" each answer one question. Typed data at the seams tells a reader exactly what one part hands to the next.

Before

The generation loop written as one long function. It works, and it's hard to read: admission, bookkeeping, error handling and the model call are interleaved, and the steps of the loop only exist as comments.

What makes it hard:

  • The shape of the loop exists only in the numbered comments.
  • Each request's state is spread across three dicts that every branch must update together.
  • Requests are untyped tuples and dicts, so you learn their fields by reading every line.
  • The helper _admit takes the caller's dicts and changes them (see chapter 4).

After

The loop in run now reads as its own description: take new requests, admit what fits, advance one step, return what finished. Each request's state lives in one Sequence. The rule for "finished" lives in one method, next to the data it reads. Error handling moved out of the loop on purpose; chapter 7 covers where it went.

Guidelines

Name the steps after what they mean, not how they work

retire_finished(), not pop_eos_or_budget(). A reader of the loop cares about the role of the step; the method body shows the mechanics.

Keep orchestration and work apart

The loop decides what happens and in which order. It shouldn't also contain the details of how. If a step needs more than a couple of lines inline, it's a method.

Typed data at every seam

Between the HTTP layer and the scheduler, between the scheduler and the model, between processes: use a @dataclass (or a protobuf or pydantic model at process boundaries). Avoid passing bare dicts and tuples with conventional positions. A dataclass is documentation the type checker enforces.

One file per concept, not per layer

A file called scheduler.py holding the scheduler is easy to find. A file called utils.py holding half of it isn't. Avoid utils, helpers, common and misc as homes for logic.
